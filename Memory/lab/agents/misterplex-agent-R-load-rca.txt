    *(0xFFC25080) = 0x3FFF     fpgaportrst — ALL f2sdram ports ON
    *(0xFFD0501C) = 0          release per2modrst
    *(0xFF800000) = 25 (0x19)  L3 REMAP
  Then print "Bitstream size: %d bytes" and return RC=0.

Kernel FPGA framework is NOT this path (HAVE, sysfs read-only):
  /sys/class/fpga_bridge: br0=lwhps2fpga enabled, br1=hps2fpga enabled,
    br2=fpga2hps enabled  — /bin/fpga never writes these.
  altera_fpga2sdram_bridge driver exists but is NOT bound
    (only bind/unbind/uevent; no device).
  DT has fpga-bridge@ffc25080 (altr,socfpga-fpga2sdram-bridge)
    — same 0xFFC25080 /bin/fpga pokes under the kernel’s feet.
  soc:base_fpga_region = waiting_for_supplier.
  fpga_manager fpga0 state=operating (read-only observe).

So /bin/fpga is a 2017 /dev/mem FPGA-manager poker that:
  - slams fpgaportrst 0 → program → fpgaportrst 0x3FFF
  - does not talk to Main
  - does not update /tmp/CORENAME or /tmp/RBFNAME
    (L-n2-idle / L-n5-gate: CORE=Plex RBFNAME=Plex STAMPED=NOT after named)
  - does not check GPI[31]
  - does not stop Main user_io / scaler / SPI
  - races the kernel’s still-“enabled” HPS-FPGA bridges

R-fpga-rca’s “FPGA-manager bridge disable/program/enable” sketch is
the right *shape* but the implementation is this raw /dev/mem tool,
not Linux FPGA-manager sysfs. Cite corrected.

5) WHAT Main load_core DOES (contrast)
================================================================
HAVE (strings /media/fat/MiSTer Version 260707 + deploy script):

  Main also mmaps /dev/mem and uses the SAME FPGA error lexicon:
    "Bitstream size: %lld bytes"
    "FPGA: Could not reset / configure / Configuration error."
    "GPI[31]==1. FPGA is uninitialized or incompatible core loaded."
    "/tmp/CORENAME" "/tmp/RBFNAME"
    "load_core "
  So Main’s programmer is the same family of FPGAMGR /dev/mem poke
  (not sysfs firmware). The difference is the *session around* it.

  load_core path (deploy_plex_core.sh DEPLOY_LOAD=menu L213–L247):
    1. Soft-stop misterplexd (SPI not mid-flight).
    2. printf 'load_core /media/fat/menu.rbf' > /dev/MiSTer_cmd
       Main is the reader. Wait CORENAME~menu (liveness test).
       Wedged Main (accepts FIFO, drops cmds) → DEPLOY_FAIL / recover.
    3. printf 'load_core /media/fat/_Utility/Plex.rbf' > /dev/MiSTer_cmd
       Wait CORENAME~plex.
    4. Main writes CORENAME/RBFNAME, checks GPI[31], inits user_io/video.
    5. Then start companion.

  Menu first is the quiet bitstream: Menu has no 720p DDR masters.
  fpgaportrst re-enable lands on a DDR-quiet core. Second load
  (product Plex.rbf) is then done *by Main*, which already owns
  user_io and will re-init after config.

  Named load_core of Plex.720p24.* skips the product-name contract:
    Main still programs, but after 720p bits GPI[31] historically
    stays 1 (incompatible / uninit) → Main Quits → FIFO hang
    (R-cmd-hang). Or HPS reboots (L-n2-gate LOAD_CORE_REBOOT).
    RBFNAME would be the named basename only if Main survives;
    run_720p24_live_gate.sh also stamps /tmp/RBFNAME by hand.

INFER (labeled): same FPGAMGR poke, different owner + prelude.
  /bin/fpga reconfigures under a live Main and instantly opens
  ALL f2sdram ports onto a 720p bitstream whose reset path
  publishes idle PLXD (R-fpga-rca path B, bank_mbox_req=1) and
  whose m1 fabric reader is enable=1. That is the idle-HPS class.
  Main+menu then Plex.rbf sequences a quiet core first and keeps
  GPI31/user_io inside one process. L-n5-menu 20s stay-up is the
  HAVE that this difference is not just theory for 4554.

  Residual risk (do not exonerate silicon): if idle 720p DDR were
  enough, menu+Plex would also die. It did not in 20s. That does
  not prove play-safe, leftover-MAGIC_P-safe, or >20s-safe.
  L-n5-play is the play measurement (not this worker).
