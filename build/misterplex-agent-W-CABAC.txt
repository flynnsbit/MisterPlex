Fmax situation:
- No Quartus synthesis/fitter was run because parent authorization is required.
- Current PLL file fpga/Plex_MiSTer/rtl/pll/pll_0002.v sets output_clock_frequency0("20.000000 MHz") for clk_sys.
- The Verilated engine issues one bin per clock when its refill bytes are available.
- At current 20 MHz clk_sys: achievable simulated rate = 20,000,000 bins/s.
  Margin vs mean demand = 20,000,000 / 756,520.778 = 26.44x.
  Margin vs worst-frame 40 ms budget = 20,000,000 / 1,834,750 = 10.90x.
  Equivalently, even at 20 MHz the entropy engine can tolerate about 10.9 clocks/bin average over the worst frame before dropping below real-time.
- Dedicated PLL case: actual Fmax is not measured without Quartus. If a dedicated CABAC clock closes at 50 MHz, margin vs worst frame is 27.25x; at 100 MHz, 54.50x. The required Fmax at 1 bin/clock for the worst frame is only 1.835 MHz.
- Critical-path estimate from RTL: one lps table lookup, subtract/compare, state table lookup, normalization/ctz/refill add/shift in a single cycle. This still needs Quartus timing sign-off, but 20 MHz is a very low bar for this datapath on Cyclone V.

Verdict:
FEASIBLE for this delivered stream at current 20 MHz clk_sys if the one-cycle arithmetic core closes timing, with measured 10.90x worst-frame margin and 26.44x mean margin. This does NOT mean a complete H.264 High-profile decoder is done: B-slice/reference management, full CABAC context derivation, residual/motion syntax plumbing, and integration remain large tasks. But the CABAC arithmetic engine rate itself is not the blocker. Authorized Quartus synthesis is still required for hard Fmax/resource sign-off; I did not run it.
